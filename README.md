# ДЗ4. Отказоустойчивость с Apache ZooKeeper

Отчёт: [ИнжДан_lab4_Вдовина А.Р.pdf](<ИнжДан_lab4_Вдовина А.Р.pdf>).

## Подготовка ансамбля

Нужны Docker и Docker Compose. Образ `zookeeper:3.9.6-jre-17` содержит
ZooKeeper 3.9.6 и Java 17. Java на компьютере отдельно устанавливать не нужно.

Все команды выполняются из папки с `compose.yaml`.

```bash
docker compose config --quiet
docker compose up -d --wait --wait-timeout 120
docker compose ps
```

Серверы имеют разные ID и отдельные тома для данных. Клиентские подключения
с macOS используют адреса `127.0.0.1:2181,127.0.0.1:2182,127.0.0.1:2183`.
Внутри сети Docker адреса — `zk1:2181,zk2:2181,zk3:2181`.

## Роли серверов

```bash
docker compose exec -T zk1 zkServer.sh status
docker compose exec -T zk2 zkServer.sh status
docker compose exec -T zk3 zkServer.sh status
```

Должен быть один `leader` и два `follower`. Конкретный номер лидера
может отличаться между запусками.

## Клиент

```bash
docker compose exec zk1 zkCli.sh -server zk1:2181,zk2:2181,zk3:2181
```

Внутри клиента доступны, например, `ls /` и `quit`.

## Журналы

Первичная проверка и фактические конфигурации сохраняются в `logs/setup/`.
В первичном запуске 5 ноября 2026 года `zk3` стал лидером, `zk1` и `zk2` —
последователями. Все три сервиса прошли проверку здоровья. Подтверждены
ZooKeeper 3.9.6 и Java 17.0.21; клиент успешно создал, прочитал и удалил
проверочный узел. Итоги — в `logs/setup/summary.json`, клиентский вывод —
в `logs/setup/client-smoke.log`. Отдельный `client-negative-check.log`
показывает ожидаемую ошибку обращения к уже удалённому узлу.

Для сохранения текущих журналов серверов:

```bash
docker compose logs --no-color --timestamps > logs/zookeeper.log
```

## Остановка и повторный запуск

```bash
docker compose stop
docker compose up -d --wait --wait-timeout 120
```

Остановка сохраняет данные в томах Docker.

## Проверка кворума и эфемерного узла

```bash
python3 scripts/ensemble_demo.py
```

Сценарий останавливает одного последователя и проверяет запись/чтение,
затем останавливает второго и проверяет отсутствие обслуживания.
В блоке `finally` все три сервера запускаются снова. После восстановления
проверяются сохранённые данные и эфемерный узел: отдельный клиент видит
его, пока сессия владельца открыта; после `quit` владельца узел отсутствует.
Журналы и `summary.json` находятся в `logs/ensemble/<run-id>/`.

## Координаторы расчёта

Нужен Python 3.10 или новее; опыты выполнены на Python 3.14.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Полный набор версий зависимостей использованного окружения сохранён
в `requirements.lock`; для точного повторения можно установить его.

Нужен полный `it_vacancies_2024.csv` из ДЗ3. Ссылка на файл курса:
https://drive.google.com/file/d/1rLEu3N2isIBhAkK1EcSJ2482ouOPAots/view

Положить файл в `work/it_vacancies_2024.csv` или передать путь через
`--source`. Размер: 847 619 384 байта. SHA-256:

```text
303db922b541e4440906f5a7e8be32fb55e8808f950ffddb8c272f1548212a65
```

В этой работе исходный CSV читается локально; он совпадает с объектом S3
из ДЗ3 по SHA-256. Фильтр, нормализация навыков, разбиение CSV и map-функция
взяты без изменений из ДЗ3: `hw3/PROVENANCE.md`. Координатор использует
результат для пар навыков (`k=2`). Сам CSV, окружение и рабочие снимки
не входят в Git.

### Автоматическое воспроизведение обоих опытов

```bash
.venv/bin/python scripts/failover_demo.py
```

По отдельности:

```bash
.venv/bin/python scripts/failover_demo.py --mode 0
.venv/bin/python scripts/failover_demo.py --mode 1
```

Сценарий запускает A и B с `FENCING=0` либо `FENCING=1`, ждёт чекпоинт,
приостанавливает PID A через SIGSTOP минимум на 40 с, ждёт завершения B
и возобновляет A через SIGCONT. Оба используют сессию ZooKeeper 10 с.
Время смены лидера считается по монотонным временным меткам. Задержка
0,12 с после чанка нужна для воспроизводимости опыта и не меняет частоты.

Журналы A/B, стандартный вывод процессов, PID/сигналы, результат сверки
и состояние указателя находятся в `logs/failover/<run-id>/`.
Сценарий сравнивает все частоты обоих кандидатов с `baseline/counts_2.json`.
Контроль: 3 123 вакансии, 13 552 уникальные пары, 61 694 вхождения.

### Ручной запуск одного координатора

```bash
FENCING=1 .venv/bin/python -m hw4.coordinator \
  --id A \
  --hosts 127.0.0.1:2181,127.0.0.1:2182,127.0.0.1:2183 \
  --root /hw4/runs/manual-example \
  --source work/it_vacancies_2024.csv \
  --work work/manual-example \
  --log logs/manual-A.log
```

Во втором терминале выполнить ту же команду с `--id B` и
`--log logs/manual-B.log`. Для нового опыта использовать новый `--root`
и новый `--work`. PID лидера и события видны в журналах.

### Проверки

```bash
.venv/bin/python -m pytest tests -q
```

Часть тестов обращается к работающему ансамблю. Они проверяют возобновление
снимка, запрет повторного/пропущенного чанка, целостность и идентичность
источника, версии эпохи, обе ветки публикации, защиту чекпоинта и
запрет выдачи эпохи уже исчезнувшему кандидату.

## Как устроена защита

Лидерство приложения строится на эфемерных последовательных кандидатах;
ожидающий процесс наблюдает за предшественником. Выдача новой эпохи
транзакционно проверяет существование кандидата. Чекпоинт хранит
непрерывный префикс уже применённых чанков и соответствующие счётчики.
Сначала сохраняется файл снимка, затем указатель на него в ZooKeeper.

Официальный результат — указатель `/hw4/runs/<run-id>/result` в ZooKeeper.
Файлы кандидатов сохраняются раздельно по эпохе. При `FENCING=1` проверка
версии `/epoch` и обновление `/result` выполняются одной транзакцией;
старая эпоха получает `BadVersionError`. При `FENCING=0` обновление
безусловное, поэтому старая копия способна опубликовать результат повторно.
Устаревшие чекпоинты защищены в обоих режимах.

Старый процесс намеренно продолжает локальную работу после потери сессии,
чтобы продемонстрировать проверку на стороне получателя. Наличие двух
файлов кандидатов не означает две принятые публикации: это определяется
журналами и версией официального указателя.
